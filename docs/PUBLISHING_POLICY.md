# 工程实战内容发布规范 v1

## 1. 证据优先

只发表亲自实测或有原始测试回执的事实。记录软硬件版本、日期、输入、输出、失败症状、根因定位步骤、修复差异、复测结果和边界。

状态必须标注：`DRAFT`（草稿）、`IN_PROGRESS`（正在实验）、`VERIFIED`（阶段验收通过）、`RELEASED`（内容已发布）。`RELEASED` 只代表文章公开，不代表相关软件生产上线。

## 2. 发布四道门禁

1. **来源**：对应私有工程的原始命令/日志/提交/测试报告可追溯；不要从回忆推断测试结论。
2. **隐私与安全**：清除真实客户信息、会话内容、手机号、Token、密钥、用户主目录、内网/公网 IP、域名密钥、硬件序列号、原始屏幕截图。
3. **可复现与授权**：发布的命令默认安全、可运行、明确适用版本，不包含商业片源、未经许可素材、平台绕过手段。
4. **成果准确性**：清楚区分「推理引擎可启动」和「完整模型加载成功」、「单次弱网实测通过」和「生产环境稳定性已证明」。

## 3. 内容流水线

私有工程日志 → 提取脱敏证据 → 问题卡片 → 文章草稿 → 技术核对 → 隐私/授权检查 → GitHub 发布 → 官网摘要 → 社媒短帖 → 定期更新勘误。

文章可传播至官网技术栏目、开发者社区、公众号、海外社媒，但不同平台根据受众制作短文和摘要，原文链接统一引用本仓库；不批量重复灌水。当前**不宣称各平台自动发布已经开通**。

## 4. 可重复使用内容模板

标题：平台 + 问题/技术 + 可核验结果。

- 为什么做这个实验？
- 测试环境与版本。
- 重现步骤、原始问题、误判因素。
- 根因排查、修复方法。
- 最终真实验证数据。
- 尚未证明什么。
- 最小复现命令/脚本（可选）。
- 版本与更新日志。

## 5. 内容边界

不能未经审查自动从私有仓库复制代码、配置、日志、截图或订单。品牌技术博客服务于发现、搜索和信任，不能为了宣传声称不存在的客户案例、线上效果或收益。第三方文章和图片不要大段转载。
